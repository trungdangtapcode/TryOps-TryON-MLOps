# Service Level Objectives

These SLOs are local-demo targets first. They should be revised after real model benchmarks.
The machine-readable source of truth is `configs/service_level_objectives.json`.

## VTON Service

- Availability target: 99% during demo window.
- p50 latency target: below 8 seconds for cached or lightweight baseline.
- p95 latency target: below 12 seconds for candidate promotion.
- Error rate target: below 2% excluding invalid user input.
- Fallback: cached seeded outputs if GPU/model runtime is unavailable.
- Rollback target: restore previous champion alias in under 2 minutes.

## LLM Service

- Availability target: 99% during demo window.
- p50 latency target: below 1.2 seconds for short prompts.
- p95 latency target: below 2.5 seconds for promotion gate.
- Throughput target: at least 20 tokens/sec for optimized candidate.
- Memory target: no more than 16 GB for the selected local model.
- Fallback: route from optimized candidate to baseline model or cached response.

## MLOps Control Plane

- Promotion decision latency: below 500 ms for local policy checks.
- Reproducibility command success: 100% for `make smoke`.
- Required evidence coverage: model card, data card, evaluation report, lineage, policy decision.
- Audit retention: every promotion decision is stored as a generated artifact.

## Error Budgets

The formal SLO config defines a 30-day reporting period and per-workload error budgets:

| Workload | Availability | Error Budget |
| --- | ---: | ---: |
| LLM | 99.0% | 1.0% |
| VTON | 99.0% | 1.0% |
| Control plane | 99.5% | 0.5% |

An event is counted as bad when it violates the workload SLI contract:

- LLM: latency over target, quality below target, or unsafe response behavior.
- VTON: latency over target or garment-similarity below target.
- Control plane: failed smoke check or endpoint latency over target.

## Native Burn-Rate Engine

Local evidence is generated by:

```bash
make slo-burn-rate-sample
```

Artifacts:

- `artifacts/eval/slo/slo_burn_rate_report.json`
- `infra/prometheus/tryops_burn_rate_alerts.yml`
- `artifacts/native/tryops_burn_rate_cli`

The native C++ engine evaluates the multi-window, multi-burn-rate pattern:

| Alert | Long Window | Short Window | Burn Rate | Severity |
| --- | ---: | ---: | ---: | --- |
| Fast burn | 1h | 5m | 14.4x | page |
| Slow burn | 6h | 30m | 6x | page |
| Ticket burn | 3d | 6h | 1x | ticket |

The generated report includes two sections:

- Current local evidence from LLM benchmark, VTON comparison, and endpoint smoke artifacts.
- A deterministic regression drill that proves page-level alerts fire when both long and short
  windows are burning the budget.

## Chaos Drill And Rollback

Local chaos evidence is generated by:

```bash
make chaos-sample
```

Artifacts:

- `artifacts/eval/chaos/chaos_drill_report.json`
- `artifacts/native/tryops_chaos_cli`
- `artifacts/deployments/vton-catvton-2026-06-11-001-production-demo/auto_rollback_record.json`

The chaos drill injects GPU OOM, slow decode, corrupted weights, and poisoned-candidate scenarios.
Each scenario is classified by the native C++ chaos evaluator, then evaluated by the native C++
burn-rate engine. Page-level burn-rate verdicts trigger the existing rollback record path.

Research basis:

- Google SRE Workbook, "Alerting on SLOs": https://sre.google/workbook/alerting-on-slos/
- Prometheus alerting practices: https://prometheus.io/docs/practices/alerting/
